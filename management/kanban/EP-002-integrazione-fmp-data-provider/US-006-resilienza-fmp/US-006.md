# US-006 — Resilienza alle indisponibilità del provider esterno

## Descrizione
Come sistema backend, voglio gestire fallimenti del data provider (errori transitori, indisponibilità, rate limit) con retry e fallback su cache, affinché l'utente continui ad avere risposte utili anche durante problemi esterni. [^src: wiki/concepts/webapp-architecture-vi.md §Requisiti Non Funzionali Rilevanti]

## Business Rules
- Errore transitorio del provider: il sistema esegue retry con un numero massimo limitato di tentativi.
- Esaurimento dei retry: se esistono dati in cache anche scaduti, il sistema li serve marcandoli come "potenzialmente non aggiornati".
- Se non esistono dati né freschi né in cache: il sistema restituisce un errore strutturato comprensibile.
- Eventi di rate limit ricevuti dal provider devono essere registrati per analisi successiva.

## UI Reference
N/A — storia infrastrutturale; l'eventuale marcatore "dati non aggiornati" verrà reso visibile dalla UI in EP-005.

## Acceptance Criteria
- [ ] In presenza di errore transitorio simulato, il sistema esegue almeno un retry prima di fallire.
- [ ] Con cache disponibile e provider indisponibile, il sistema restituisce i dati cache marcati come "potenzialmente non aggiornati".
- [ ] Senza cache e con provider indisponibile, il sistema restituisce un errore strutturato (no stack trace utente-facing).
- [ ] Eventi di rate limit del provider risultano tracciati in un canale di osservabilità (log o equivalente).
