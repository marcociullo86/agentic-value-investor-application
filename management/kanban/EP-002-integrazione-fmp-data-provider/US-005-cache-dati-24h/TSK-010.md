# TSK-010 — FmpCacheService: implementazione cache-aside TTL 24h

## Obiettivo

Implementare il layer di cache che fa da proxy tra i chiamanti (AnalyzeTickerService,
SearchService) e `FmpAdapter`, con persistenza su PostgreSQL e TTL 24h.

## Scope tecnico

- `FmpCacheService.getOrFetch(ticker, endpoint, fetchFn)`:
  1. Cerca in `fmp_financial_snapshot` l'entry `(ticker, endpoint)` più recente.
  2. `now - fetched_at < 24h` → ritorna payload deserializzato.
  3. Altrimenti chiama `fetchFn()`, persiste nuovo snapshot, ritorna dati freschi.
  [^src: design_&_architecture/decisions/ADR-004-fmp-integration.md §Cache layer 24h]
- `FmpCacheService.getOrFetchProfile(ticker)`: stesso pattern su `fmp_profile_snapshot`
  (TTL indicato 1h per profilo/prezzo corrente).
  [^src: design_&_architecture/data/er-diagram.md §fmp_profile_snapshot]
- `FmpCacheService.getStale(ticker, endpoint)`: cerca snapshot anche scaduti per fallback
  US-006.
- Repository JPA `FmpFinancialSnapshotRepository` e `FmpProfileSnapshotRepository`.
- Response `FinancialDataset` include sempre `dataSnapshotAt` (US-005 AC "timestamp dati al").
  [^src: management/kanban/EP-002-integrazione-fmp-data-provider/US-005-cache-dati-24h/US-005.md §AC]

## Vincoli e note

- Eviction/invalidazione non deve generare errori bloccanti per analisi in corso (US-005 AC).
- `StockRepository` deve upsertare `stocks` row quando viene fetchato il profilo per un
  nuovo ticker (lazy population catalogo).

## Criteri di completamento (DoD)

- [ ] Seconda analisi dello stesso ticker entro 24h non genera nuova chiamata a FmpAdapter
  (verificato via spy mock).
- [ ] Analisi oltre 24h genera nuova chiamata.
- [ ] `dataSnapshotAt` presente in risposta.
- [ ] Unit test con orologio virtualizzato (Clock bean) per simulare scadenza TTL.
