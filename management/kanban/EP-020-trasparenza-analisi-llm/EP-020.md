# EP-020 — Trasparenza analisi LLM nel verdetto Deep Analysis

> Rendere visibile e comprensibile *perché* un titolo riceve un certo verdetto: esporre la sintesi narrativa dell'LLM nel verdetto, arricchire il Rapporto Munger con la motivazione, mostrare le notizie effettivamente analizzate (titolo + testo) nel Sentiment News, e tracciare nei log l'intera interazione LLM (prompt + risposte) per audit e debug.

## Obiettivo

La deep analysis (`GET /api/analysis/{ticker}/deep?invoke_llm=true`) effettua 11 chiamate LLM (10 query Munger + 1 sintesi) più la sintesi news, ma:
- nei log appare solo `llmCalls=11` — **nessuna visibilità** su prompt inviati e risposte ricevute;
- il verdetto mostra solo una `motivazioneAggregata` deterministica breve, **senza la sintesi narrativa** del modello che spieghi il "perché";
- il blocco Sentiment News mostra **solo conteggi** (Panic/Structural/Neutral), non le notizie analizzate;
- il Rapporto Munger mostra liste di item ma **non la narrativa** di sintesi.

L'epica colma questi gap, prendendo come riferimento UX il report HTML di `agent.py` (dropdown che espande il dettaglio completo dell'interazione LLM: classificazione + motivazione + segnali chiave per news, e RISCHIO + motivazione + rischi/forza/segnali per Munger).

## Valore di business

- **Fiducia e spiegabilità**: l'investitore capisce *perché* il bot dà quel verdetto, non solo *cosa* — coerente con l'approccio value (decisione motivata, non black-box).
- **Auditabilità**: i prompt/risposte LLM nei log permettono di verificare la qualità del ragionamento e fare debug dei costi (11 call/ticker).
- **Densità informativa**: le notizie analizzate (titolo+testo) e la sintesi Munger danno all'utente il contesto qualitativo che oggi resta nascosto nel `report_json`.

## Parallelizzazione (waves)

- **Wave 1 (parallela)** — fondamenta backend/contratto, file disgiunti:
  - US-088 → TSK-299 (be, logging) — *indipendente da tutto*
  - US-089 → TSK-300 (be+contratto, campo `sintesi` Munger)
  - US-091 → TSK-305 (db, migration snippet) → poi TSK-306 (be+contratto news)
- **Wave 2 (parallela)** — frontend, dopo che openapi+tipi FE sono aggiornati:
  - US-089 → TSK-301 (fe verdetto), US-090 → TSK-303 (fe Munger detail), US-091 → TSK-307 (fe news list)
- **Wave 3 (parallela)** — QA/test/E2E:
  - TSK-302, TSK-304, TSK-308

Nota scheduler `code_path_conflict: strict`: TSK-300 e TSK-306 toccano file backend disgiunti (MungerInversionAnalyzer/DeepAnalysisService vs NewsSentimentService) → parallelizzabili; i TSK FE toccano componenti distinti → parallelizzabili.
