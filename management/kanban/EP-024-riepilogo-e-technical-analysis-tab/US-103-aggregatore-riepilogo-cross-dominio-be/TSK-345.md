# TSK-345 — Infra: wiki/ disponibile al runtime per il corpus RAG WIKI

## Obiettivo

Rendere le pagine markdown di `wiki/concepts/` e `wiki/syntheses/` accessibili **a runtime** al `WikiCorpusIndexer` (TSK-337), sotto il path atteso dalla property `rag.wiki.corpus-path` (default `/app/wiki`). Senza questo intervento l'endpoint `POST /admin/rag/wiki/reindex` degrada a 0 pagine indicizzate (WARN) e le citazioni RAG cross-dominio del Riepilogo (US-103) non funzionano in produzione.

Chiude il gap `be-wiki-runtime-corpus-mount` (vedi `wiki/gaps.md` 2026-06-08).

## Scope

### Immagine runtime self-contained (default prod)
- `src/docker/Dockerfile`, stage `runtime` (Temurin 21 JRE alpine, `WORKDIR /app`): aggiungere `COPY wiki/ /app/wiki/` accanto a `COPY --from=... /app/app.jar` e `/app/public/`. Coerente con `rag.wiki.corpus-path` default `/app/wiki`.
- Verificare che `chown -R appuser:app /app` (riga esistente) copra anche `/app/wiki` (read è sufficiente per l'indexer).
- **Verificare `.dockerignore`**: assicurarsi che `wiki/` NON sia escluso dal build context (altrimenti la `COPY` fallisce o copia vuoto). Se escluso, eccettuare `wiki/concepts/` e `wiki/syntheses/`.

### Dev/aggiornabilità senza rebuild (opzione complementare)
- In `src/docker/docker-compose.yml` (servizio `app`): valutare un bind-mount read-only `./wiki:/app/wiki:ro` cosicché in dev il corpus sia aggiornabile e re-indicizzabile (`/admin/rag/wiki/reindex`) senza rebuild dell'immagine. In `docker-compose.prod.yml` preferire l'immagine self-contained (no bind-mount, riproducibilità).
- Il path è già override-abile via env `RAG_WIKI_CORPUS_PATH` (WikiCorpusProperties): non serve cablare nulla nel BE.

### Coerenza multi-compose
- Allineare anche `docker-compose.gpu.yml` e `docker-compose.local-no-embeddings.yml` se ridefiniscono il servizio `app` in modo da perdere il path (nel caso, stessa scelta del compose base).

## Invarianti / non-regressione
- Nessuna modifica al BE (l'indexer e la property esistono già da TSK-337).
- L'avvio dell'app resta verde anche se per qualche ragione `wiki/` è assente (degrade WARN già implementato in TSK-337): questo task elimina il degrade in prod, non introduce un fail-fast.
- Nessun impatto sugli altri stage (`fe-build`, `be-build`) né sugli asset FE/openapi già copiati.

## Acceptance Criteria
- [ ] Lo stage `runtime` del Dockerfile copia `wiki/` (almeno `concepts/` + `syntheses/`) sotto `/app/wiki/`; `.dockerignore` non lo esclude.
- [ ] Build immagine (`podman build vi-app` / pipeline CI) verde; `/app/wiki/concepts` e `/app/wiki/syntheses` presenti nel container (verifica con `ls` nel layer runtime).
- [ ] `docker-compose.yml` (dev) monta `./wiki:/app/wiki:ro` (o documentazione esplicita se si sceglie solo la COPY); `docker-compose.prod.yml` usa l'immagine self-contained.
- [ ] Multi-compose (`gpu`, `local-no-embeddings`) coerenti: il path `/app/wiki` resta valorizzato dove il servizio `app` è ridefinito.
- [ ] Smoke: con container avviato, `POST /admin/rag/wiki/reindex` (auth ADMIN) ritorna un conteggio pagine > 0 (le pagine VI+TA dei due domini) anziché 0.
- [ ] Aggiornato `wiki/gaps.md`: gap `be-wiki-runtime-corpus-mount` marcato risolto con riferimento a TSK-345 (post-merge).
