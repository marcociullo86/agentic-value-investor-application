# US-103 — Aggregatore Riepilogo cross-dominio (BE)

## Descrizione

Come investitore value che ha aperto la pagina dettaglio di un ticker, voglio un endpoint `GET /api/analysis/{ticker}/summary` che aggreghi verdetto VI (rule engine + MoS + intrinsic value) + Deep Analysis (Munger inversion + owner earnings + moat) + Technical Analysis (entry-timing + stop + sizing) in una **raccomandazione tipata** `ENTER_NOW / WAIT_FOR_SETUP / AVOID` con rationale strutturato e citazioni cross-dominio (wiki VI + wiki TA), affinche io possa avere una risposta sintetica e azionabile alla domanda "Devo entrare ORA su questo ticker?" — la domanda esatta che il caso COPART ha lasciato senza risposta. [^src: wiki/syntheses/ta-vs-vi-decision-layer.md §"Sintesi: la regola delle due domande"] [^src: wiki/syntheses/ta-vs-vi-decision-layer.md §"La regola sequenziale"]

## Business Rules

### Endpoint

- Nuovo endpoint: `GET /api/analysis/{ticker}/summary`.
- Auth-aware coerente con `/api/analysis/{ticker}` (Vary header, cache per-user).
- Input lato BE: legge internamente i risultati di `/api/analysis/{ticker}` (VI + contextFlags), `/api/analysis/{ticker}/deep/runs/latest` (Munger report — EP-011/EP-020), `/api/analysis/{ticker}/technical` (TA — US-098..US-100). Non duplica i calcoli: orchestra.
- Lazy: se Deep Analysis non e' stata ancora eseguita per il ticker, il Summary include un campo `deepAnalysisStatus = NOT_INDEXED` invece di bloccare.
- Lazy TA: chiama internamente `/technical` (gia in cache 24h se l'utente ha aperto il tab Technical Analysis).

### Verdetto Summary — tassonomia

```
type SummaryVerdict =
  | "ENTER_NOW"
  | "WAIT_FOR_SETUP"     // VI positivo, TA o Deep sfavorevole → attendere
  | "AVOID"              // VI negativo → mai entrare, indipendentemente da TA
  | "INSUFFICIENT_DATA"  // dati troppo lacunosi
```

### Tabella di mapping (gate VI hardcoded)

**Il gate primario VI e' hardcoded in Kotlin, non delegato a LLM.** Tabella deterministica:

| VI verdict (TrafficLightPanel aggregato) | MoS | Deep Analysis verdict | TA entryTiming | Summary verdict |
|---|---|---|---|---|
| GREEN dominante (≥ 8/13 GREEN, MoS GREEN) | GREEN | OK o NOT_AVAILABLE | ENTRY_FAVORABLE o ENTRY_NEUTRAL | `ENTER_NOW` |
| GREEN dominante | GREEN | OK | WAIT o ENTRY_UNFAVORABLE | `WAIT_FOR_SETUP` |
| GREEN dominante | GREEN | RISCHIO_ESTREMO | qualsiasi | `AVOID` (Munger overrides) |
| GREEN dominante | YELLOW | OK | ENTRY_FAVORABLE | `WAIT_FOR_SETUP` (MoS marginale, aspettare prezzo migliore) |
| YELLOW dominante (4-7 GREEN) | qualsiasi | qualsiasi | qualsiasi | `WAIT_FOR_SETUP` o `AVOID` (decisione su MoS) |
| RED dominante (< 4 GREEN) | qualsiasi | qualsiasi | qualsiasi | `AVOID` (gate VI primario) |
| INDETERMINATE dominante (>=4 segnali INDETERMINATE/NOT_CALCULABLE) | qualsiasi | qualsiasi | qualsiasi | `INSUFFICIENT_DATA` |

**Regola assoluta:** un titolo con VI verdict RED non puo mai diventare `ENTER_NOW`, indipendentemente da quanto favorevole sia la TA. Un titolo con Munger `RISCHIO_ESTREMO` non puo mai diventare `ENTER_NOW`, indipendentemente da VI + TA. [^src: wiki/syntheses/ta-vs-vi-decision-layer.md §"La regola sequenziale"] [^src: wiki/concepts/munger-inversion-rag.md §Cascade Logica]

  "summaryVerdict": "WAIT_FOR_SETUP",
  "viVerdict": "GREEN_DOMINANT",      // VI verdict aggregato
  "deepAnalysisStatus": "AVAILABLE",   // o NOT_INDEXED / NOT_AVAILABLE
  "deepVerdict": "OK",                 // da Munger cascade
  "taVerdict": "WAIT",                 // da US-099
  "rationale": {
    "viSummary": "Verdetto fondamentale positivo: 10/13 ruleId GREEN, MoS 28%, DCF $X.X vs prezzo $Y.Y.",
    "deepSummary": "Owner earnings positive, moat strong, no Munger red flags.",

  },
  "reentryCondition": {
    "code": "RSI_BELOW_50",
    "description": "Re-valuta quando RSI 14d rientra sotto 50"
  },
  "wikiCitations": [
    { "id": "ta-vs-vi-decision-layer", "anchor": "la-regola-sequenziale", "domain": "technical-analysis-trading" },
    { "id": "ta-entry-timing-stock-detail", "anchor": "screen-2-pullback-nel-trend-rsi", "domain": "technical-analysis-trading" },
    { "id": "value-investing-rule-engine", "anchor": "output-del-rule-engine", "domain": "value-investing" },
    { "id": "margin-of-safety", "anchor": null, "domain": "value-investing" }
  ],

Il campo `warningAntiCopart` e' presente **solo** quando: `viVerdict ∈ {GREEN_DOMINANT}` AND `taVerdict ∈ {WAIT, ENTRY_UNFAVORABLE}` AND `summaryVerdict = WAIT_FOR_SETUP`. In tutti gli altri casi assente.

### Citazioni RAG cross-dominio

- Riuso pgvector + arctic-embed-l-v2 sidecar (EP-011 TSK-099/100/102). Le pagine wiki vengono indicizzate come **secondo corpus** nel vector store (oltre ai filing 10-K/10-Q gia indicizzati). Lo scope dell'indicizzazione iniziale: tutte le pagine in `wiki/concepts/` e `wiki/syntheses/` con frontmatter `domain ∈ {value-investing, technical-analysis-trading}`.
- Pattern di recupero: simile a Munger inversion (EP-011 TSK-105) ma con query strutturate sui 3 verdetti (VI/Deep/TA) per recuperare i passaggi wiki rilevanti.
- L'LLM (Claude Opus, riuso `AnthropicClient` EP-011 TSK-104) genera **solo** il testo narrativo dei 3 campi `rationale.viSummary`, `rationale.deepSummary`, `rationale.taSummary` partendo dai dati strutturati. **Il verdetto `summaryVerdict` non e' mai prodotto dall'LLM**: e' deterministico Kotlin dalla tabella di mapping.
- Le citazioni `wikiCitations` sono prodotte dalla similarity search RAG (top-K=4, K configurabile) sul corpus wiki, filtrate per dominio coerente con il rationale.
- Logging gated delle interazioni LLM coerente con EP-020 US-088.
- Costo LLM: riuso `LlmBudgetGuard` + `LlmCostCounterService` di EP-011 TSK-156. La chiamata di Summary e' una sola call LLM (1 prompt → 1 risposta strutturata), non 11 come Munger.

### Caching

- Cache Summary per `(userId, ticker, viSnapshot, taSnapshot, deepSnapshot)` con TTL 24h o invalidazione su nuova run di Deep / nuova analisi VI. Pattern coerente con cache `/api/analysis/{ticker}` e snapshot Deep.

### Allineamento epic in flight

- **EP-021 (RuleSignal typed)**: se `done`, il VI snapshot legge i 13 ruleId tipati; altrimenti pattern legacy.
- **EP-023 (Net-Net NCAV)**: se `done`, i due nuovi ruleId (`NCAV_LATEST`, `NET_NET_RATIO`) entrano nel conteggio del VI verdict aggregato (i.e. la regola "≥ 8/13 GREEN" diventa "≥ X/15 GREEN" con X ricalibrato in handoff — decisione da documentare in ADR).

## UI Reference

## Acceptance Criteria

- [ ] Esiste endpoint `GET /api/analysis/{ticker}/summary` con response `SummaryVerdictResponse` come sopra documentato.
- [ ] Verdetto `summaryVerdict` calcolato in pure-function Kotlin dalla tabella di mapping; test unitari coprono **tutte le righe** della tabella (almeno 10 casi).
- [ ] Caso "VI RED + TA FAVORABLE → AVOID": verificato esplicitamente — la TA non puo promuovere un titolo VI-negativo.
- [ ] Caso "VI GREEN + Munger RISCHIO_ESTREMO → AVOID": verificato esplicitamente — Munger overrides.
- [ ] Caso "VI GREEN + TA WAIT → WAIT_FOR_SETUP con warningAntiCopart non vuoto": questo e' il test-anchor che incarna la motivazione dell'epica.
- [ ] Campo `reentryCondition` presente quando `summaryVerdict = WAIT_FOR_SETUP` e taVerdict = WAIT, propagato da US-099.
- [ ] Campo `warningAntiCopart` presente **solo** nelle condizioni esatte specificate.
- [ ] `wikiCitations` non vuote per i verdetti con dati sufficienti, con almeno una citazione per dominio (`value-investing` e `technical-analysis-trading`) quando entrambi i layer hanno contribuito al verdetto.
- [ ] L'LLM non produce mai il `summaryVerdict`: test che verifica che cambiando solo il testo del prompt (mantenendo input strutturati) il verdetto resti invariato.
- [ ] Logging gated (EP-020 US-088) attivo per la call LLM di rationale generation.
- [ ] `LlmBudgetGuard` rispettato; la call e' contabilizzata in `llm_cost_tracking`.
- [ ] Caching della Summary funziona: seconda chiamata con stessi snapshot serve da cache (test integration).
- [ ] Caso `deepAnalysisStatus = NOT_INDEXED`: il Summary continua a funzionare con verdetto basato solo su VI + TA, con `deepVerdict = null` esplicito; il rationale chiarisce che la Deep Analysis non e' stata indicizzata.
- [ ] Schema OpenAPI aggiornato con enum tipati (`SummaryVerdict`, `ViVerdict`, `DeepVerdict`, `TaVerdict`, `ReentryConditionCode`).
- [ ] Contract test OpenAPI drift `passed`.
- [ ] Javadoc/kdoc del servizio cita [[ta-vs-vi-decision-layer]] §"La regola sequenziale" e [[munger-inversion-rag]] §Cascade Logica.
