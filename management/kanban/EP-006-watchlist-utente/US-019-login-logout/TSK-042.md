# TSK-042 — Contract-test: generic-error login e 409 register

## Context

ADR-010 §2 formalizza la **generic error policy**: email inesistente e password errata devono produrre risposta `401` con body identico `"Invalid email or password"`. Questo è un AC verificabile staticamente solo confrontando i due corpi — ADR-010 lo dichiara obbligatorio come contract-test in regression suite. Contestualmente, verificare che il 409 per email duplicata sia documentato in OpenAPI.
[^src: management/kanban/EP-006-watchlist-utente/US-019-login-logout/US-019.md §Acceptance Criteria]
[^src: design_&_architecture/decisions/ADR-010-auth-consolidation.md §2. Login/logout (US-019) — generic error policy]

## Technical Specs

- **QA:** Suite di contract-test Spring MVC Test (o RestAssured con Testcontainers) per `POST /api/auth/login`.
- **Test 1 — email inesistente:** request con email non registrata + password qualsiasi → risposta `401`, body `{ "detail": "Invalid email or password" }`, `type=https://api/errors/invalid-credentials`.
- **Test 2 — password errata:** request con email registrata + password sbagliata → risposta `401`, body `{ "detail": "Invalid email or password" }`, `type=https://api/errors/invalid-credentials`.
- **Asserzione critica:** i campi `type`, `status`, `detail` dei due corpi devono essere **identici** (contract invariant).
- **Test 3 — OpenAPI drift:** verificare che `POST /api/auth/register` documenti lo status `409` con schema `ProblemDetail` in `design_&_architecture/api/openapi.yaml`. Se assente, aggiornare l'OpenAPI spec (oppure aprire follow-up sulla discrepanza).
- **Standards:** RFC 9457 Problem Details per il formato body.
[^src: design_&_architecture/decisions/ADR-010-auth-consolidation.md §2. Login/logout (US-019) — generic error policy]
[^src: design_&_architecture/decisions/ADR-007-api-contract.md §Error format]

## Implementation Steps

1. Creare (o estendere) `AuthControllerContractTest.kt` in `src/backend/src/test/`.
2. Setup: utente registrato via `authService.register(...)` nel `@BeforeEach`.
3. Scrivere Test 1: login con email inesistente → 401, body check.
4. Scrivere Test 2: login con email registrata + password errata → 401, body check.
5. Asserzione di equivalenza: `assert(body1.detail == body2.detail && body1.type == body2.type)`.
6. Verificare l'OpenAPI spec e aprire nota di follow-up se il `409` su `/register` non è documentato.

## Definition of Done

- [ ] Test 1 (email inesistente) → `401` con `detail="Invalid email or password"`.
- [ ] Test 2 (password errata) → `401` con `detail="Invalid email or password"`.
- [ ] Asserzione di equivalenza dei corpi supera.
- [ ] Test sono in regression suite (eseguiti da CI).
- [ ] OpenAPI `POST /api/auth/register` documenta il `409` o è aperto follow-up formale.
