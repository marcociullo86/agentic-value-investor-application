# US-059 — Middleware Correlation ID end-to-end

## Descrizione
Come sviluppatore in triage, voglio che ogni richiesta HTTP sia tracciata con un Correlation ID univoco (`X-Correlation-Id`) propagato dal frontend al backend e incluso in tutti i log della richiesta, affinché possa ricostruire l'intera catena di eventi di una singola richiesta utente con un solo filtro. [^src: wiki/concepts/correlation-id-tracing.md §Meccanismo di propagazione]

## Business Rules
- Un middleware/filter backend intercetta ogni richiesta HTTP in ingresso.
- Se l'header `X-Correlation-Id` è presente nella richiesta, viene propagato; altrimenti il backend genera un UUID v4.
- Il Correlation ID viene inserito nel contesto diagnostico del logger, ereditato da tutti i log prodotti durante la richiesta.
- La response HTTP include l'header `X-Correlation-Id` per permettere al client di catturarlo.
- Il Correlation ID coesiste con `traceId` e `spanId` (tracing distribuito infrastrutturale): il primo è applicativo e visibile all'utente finale, i secondi sono per tool di APM.
- Il Correlation ID è presente nel 100% dei log generati durante una richiesta HTTP.
[^src: wiki/concepts/correlation-id-tracing.md §Backend: inclusione nei log]

## UI Reference
Nessuna — storia backend con header HTTP.

## Acceptance Criteria
- [ ] Ogni richiesta HTTP senza header `X-Correlation-Id` genera un UUID v4 e lo include nella response.
- [ ] Ogni richiesta HTTP con header `X-Correlation-Id` propaga lo stesso valore nella response.
- [ ] Il 100% dei log generati durante una richiesta HTTP contiene il campo Correlation ID.
- [ ] Test di integrazione: due richieste concorrenti producono log con Correlation ID distinti.
- [ ] Il Correlation ID appare nelle risposte di errore RFC 9457 come campo strutturato.
