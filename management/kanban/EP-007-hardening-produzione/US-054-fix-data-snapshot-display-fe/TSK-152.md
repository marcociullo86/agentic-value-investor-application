# TSK-152 — analysis/[ticker]/page.tsx: uso di formatSnapshotDate per dataSnapshotAt

## Context

US-054 richiede che il campo "Dati al" nella pagina di analisi del ticker mostri una data leggibile invece del numero epoch a 13 cifre. Questo task sostituisce il rendering grezzo di `dataSnapshotAt` con la chiamata a `formatSnapshotDate` (creata in TSK-151), e verifica tutti gli altri punti di visualizzazione date nella stessa schermata.
[^src: management/kanban/EP-007-hardening-produzione/US-054-fix-data-snapshot-display-fe/US-054.md §Business Rules]
[^src: management/kanban/EP-007-hardening-produzione/US-054-fix-data-snapshot-display-fe/US-054.md §Acceptance Criteria]

## Technical Specs

- **File primario:** `src/frontend/app/analysis/[ticker]/page.tsx`
  - Individuare il punto dove `data.dataSnapshotAt` (o nome equivalente nel tipo di risposta) viene renderizzato — probabile pattern: `{data.dataSnapshotAt}` o `{String(data.dataSnapshotAt)}`.
  - Sostituire con: `{formatSnapshotDate(data.dataSnapshotAt)}`.
  - Importare `formatSnapshotDate` da `@/lib/format-date` (alias Next.js).
- **Verifica backend serializzazione:** prima di applicare il fix, leggere la risposta reale di `GET /api/analysis/AAPL` (o controllare `JacksonObjectMapperFactory.kt` / `application.yaml` per `spring.jackson.serialization.write_dates_as_timestamps`) per confermare se `dataSnapshotAt` arriva come long o come ISO string. Documentare il formato trovato in un commento inline nel sorgente.
- **Verifica altri punti di display date:**
  - Cercare nel file `page.tsx` e nei componenti importati (`TrafficLightPanel`, `ValuationSummary`, o simili) altri campi data/timestamp che usano rendering grezzo (pattern: `{data.xxxAt}` o `{data.xxxDate}`).
  - In scope solo se condividono lo stesso componente di formattazione (US-054 §Business Rules). Se trovati, applicare `formatSnapshotDate` o un formattatore analogo; se usano formati diversi, documentare in un commento `// TODO: verificare formato` senza toccare.
  - Particolare attenzione al timestamp del prezzo di valutazione (`priceTimestamp` o simile): non introdurre regressioni.
- **Tipo TypeScript:** verificare che il tipo di `data.dataSnapshotAt` nel tipo di risposta API (`AnalysisResultDto` o simile) sia `number | string` — se è dichiarato come `number` solamente, aggiornare il tipo a `number | string` per gestire entrambe le forme backend.

## Implementation Steps

1. Aprire `src/frontend/app/analysis/[ticker]/page.tsx`.
2. Individuare il rendering di `dataSnapshotAt` e aggiungere l'import + sostituire con `formatSnapshotDate(data.dataSnapshotAt)`.
3. Verificare il formato effettivo di serializzazione BE (long vs ISO) leggendo la configurazione Jackson o interrogando l'endpoint.
4. Aggiungere commento inline: `// dataSnapshotAt: backend serializza come [epoch ms | ISO-8601] — formatSnapshotDate gestisce entrambi`.
5. Cercare altri campi timestamp nella stessa schermata e applicare la policy sopra.
6. Verificare compilazione TypeScript: `npx tsc --noEmit`.
7. Avviare il dev server (`npm run dev`) e navigare `/analysis/AAPL` — verificare visivamente il campo "Dati al".

## Definition of Done

- [ ] Il campo "Dati al" su `/analysis/{ticker}` mostra una data nel formato "GG mmm AAAA, HH:MM UTC" (es. "22 mag 2026, 11:12 UTC"), non un numero a 13 cifre.
- [ ] Nessun numero epoch grezzo visibile nella schermata per il campo dataSnapshotAt.
- [ ] Il timestamp del prezzo di valutazione e gli altri campi data esistenti non sono regrediti.
- [ ] TypeScript compila senza errori.
- [ ] Commento inline con il formato di serializzazione BE rilevato.
