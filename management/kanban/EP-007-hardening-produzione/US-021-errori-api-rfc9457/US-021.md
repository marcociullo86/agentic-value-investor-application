# US-021 — Errori API con extension fields al top-level (RFC 9457)

## Descrizione
Come consumatore delle API di analisi e ricerca, voglio che i campi extension degli errori strutturati (es. ticker, timestamp) compaiano come fratelli di `type`, `title`, `status` e `detail` nel body JSON, affinché i client conformi a RFC 9457 §3.2 non debbano navigare un oggetto `properties` annidato.

## Business Rules
- Gli errori `application/problem+json` espongono extension members al top-level, non sotto una chiave `properties`.
- I campi extension esistenti (ticker, timestamp, reason, ecc.) restano invariati semanticamente; cambia solo la posizione nel payload.
- I test di contratto e integrazione esistenti vanno aggiornati per assertare il path top-level (es. `$.ticker` invece di `$.properties.ticker`).
- Retrocompatibilità opzionale: se richiesta da Arch, documentare periodo di transizione dual-read lato client interno.

## UI Reference
N/A — storia backend/contratto; il client interno consuma gli stessi endpoint di analisi e ricerca.

## Acceptance Criteria
- [ ] Risposta errore 404 su ticker inesistente espone `ticker` al top-level del body problem+json.
- [ ] Nessun campo extension rilevante resta annidato sotto `properties` nelle risposte degli endpoint analisi e ricerca coperti da contract-test.
- [ ] Contract-test e test integrazione verdi con assert su path top-level.
- [ ] OpenAPI / esempi errore aggiornati se presenti nel contratto canonico.
