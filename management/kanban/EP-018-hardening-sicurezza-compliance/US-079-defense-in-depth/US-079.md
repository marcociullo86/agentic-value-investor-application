# US-079 — Enforcement defense-in-depth

## Descrizione
Come security auditor, voglio che il backend applichi validazione input server-side indipendente dal client, filtri i dati restituiti in base ai permessi dell'utente, e non replichi business logic critica sul client come fonte di verità, affinché un attaccante che bypassa il frontend non possa accedere a dati o operazioni non autorizzate. [^src: wiki/concepts/fintech-security-compliance.md §5.3 — Defense in depth]

## Business Rules
- L'AuthGuard frontend è una feature di UX, non un controllo di sicurezza: la sicurezza è enforcement esclusivo del backend.
- Il backend filtra i dati in base ai permessi dell'utente: il frontend non riceve mai dati che l'utente non ha diritto di vedere.
- Validazione input sempre presente lato server, indipendentemente dalla validazione client.
- Nessuna business logic critica (calcolo commissioni, limiti di transazione, eligibility) è replicata sul client come fonte di verità.
- Ogni endpoint protetto rifiuta richieste non autorizzate con risposta appropriata (401/403) indipendentemente dall'header o dal cookie di origine.
[^src: wiki/concepts/fintech-security-compliance.md §5.3 — Defense in depth]

## Acceptance Criteria
- [x] Un endpoint protetto chiamato senza token valido (curl diretto) restituisce 401.
- [x] Un endpoint protetto chiamato con token di utente senza permessi restituisce 403.
- [x] Un endpoint che restituisce dati specifici per utente non include dati di altri utenti (verificato con 2 utenti concorrenti).
- [x] La validazione input server-side rifiuta payload invalidi anche se il frontend non li invia normalmente (verificato con payload crafted).
- [x] Nessun calcolo critico (es. Margin of Safety, Graham Number) è eseguito solo client-side.
