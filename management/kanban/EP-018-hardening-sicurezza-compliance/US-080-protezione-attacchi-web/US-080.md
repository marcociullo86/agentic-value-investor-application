# US-080 — Protezione contro attacchi web

## Descrizione
Come security auditor, voglio che l'applicazione implementi una Content Security Policy rigorosa (no `unsafe-inline` su script), protezione CSRF tramite cookie `SameSite=Strict` + token CSRF su richieste state-changing, e sanitizzazione output con framework che fa escape di default, affinché i vettori di attacco XSS e CSRF siano mitigati sistematicamente. [^src: wiki/concepts/fintech-security-compliance.md §5.5 — Threat model di baseline]

## Business Rules
- **XSS:** Content Security Policy rigorosa con `script-src` senza `unsafe-inline`; sanitizzazione output; framework frontend con escape di default.
- **CSRF:** Cookie `SameSite=Strict` + token CSRF su tutte le richieste state-changing (POST, PUT, DELETE, PATCH).
- La CSP è configurata come header HTTP (non meta tag) e copre: `script-src`, `style-src`, `img-src`, `connect-src`, `font-src`, `frame-src`.
- La CSP non blocca il funzionamento dell'applicazione (test E2E passano con CSP attiva).
[^src: wiki/concepts/fintech-security-compliance.md §5.5 — Threat model di baseline]

## Acceptance Criteria
- [x] L'header `Content-Security-Policy` è presente su tutte le risposte HTTP con `script-src` senza `unsafe-inline`.
- [x] Un tentativo di XSS reflected (payload `<script>alert(1)</script>` in query param) è bloccato dalla CSP.
- [x] Un POST senza token CSRF valido restituisce errore (403 o 400).
- [x] I cookie di sessione hanno `SameSite=Strict`.
- [x] Tutti i test E2E esistenti passano con CSP attiva (nessuna regressione funzionale).
- [x] La CSP è configurata come header HTTP (verificato nell'output di curl/DevTools).
