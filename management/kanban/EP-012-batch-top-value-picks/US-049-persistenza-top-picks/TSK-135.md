# TSK-135 — Migration V016__top_value_picks — tabella top_value_picks con PK composta + indice secondario

## Cosa fare

1. Creare `V016__top_value_picks.sql` in `./src/backend/src/main/resources/db/migration/`.
   (Nota: verificare la numerazione corretta; V016 potrebbe essere occupata da `deep_analysis_event_log` di TSK-119. In tal caso usare V018.)
2. La migrazione crea:
   ```sql
   CREATE TABLE top_value_picks (
     run_date         DATE         NOT NULL,
     rank             INT          NOT NULL CHECK (rank BETWEEN 1 AND 30),
     ticker           VARCHAR(20)  NOT NULL,
     verdict_class    VARCHAR(30)  NOT NULL,
     score_mos        DECIMAL(8,4),
     position_size_pct DECIMAL(6,4),
     market_cap_usd   BIGINT,
     sector           VARCHAR(100),
     sources_json     JSONB,
     verdict_payload  JSONB,
     created_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
     PRIMARY KEY (run_date, rank)
   );
   CREATE INDEX idx_top_value_picks_ticker_date ON top_value_picks (ticker, run_date DESC);
   ```
3. Aggiungere un job di pulizia separato in `application.yaml` (`@Scheduled(cron = "0 0 3 * * SUN")`) che elimina record con `run_date < now() - 365 giorni`.

## Acceptance Criteria

- [ ] Migration applicata senza errori.
- [ ] `PRIMARY KEY (run_date, rank)` applicata.
- [ ] Insert di 30 record con `rank 1..30` va a buon fine.
- [ ] Insert duplicato su `(run_date, rank)` → errore PK.
- [ ] Indice secondario presente.
