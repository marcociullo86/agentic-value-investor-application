# US-049 — Persistenza risultati batch (tabella `top_value_picks`)

## Descrizione
Come sistema backend, voglio una tabella `top_value_picks` con primary key `(run_date, rank)` che memorizzi i 30 candidati giornalieri prodotti dal job (US-048), inclusi verdetto, MoS, settore, market cap e payload originale, affinché l'endpoint pubblico (US-050) e il frontend (US-051) possano consultare le classifiche storiche senza dipendere dall'esecuzione del job. [^src: wiki/concepts/webapp-architecture-vi.md §Architettura applicativa]

## Business Rules
- Nuova tabella relazionale `top_value_picks` con colonne (minime): `run_date` (DATE, UTC), `rank` (INT, 1-30), `ticker` (VARCHAR), `verdict_class` (VARCHAR, enum 6 valori US-044), `score_mos` (DECIMAL, Margin of Safety percentage), `position_size_pct` (DECIMAL), `market_cap_usd` (BIGINT), `sector` (VARCHAR), `sources_json` (JSONB con breakdown: screener/13f/news_scout/panic_buy), `verdict_payload` (JSONB, snapshot del payload US-044), `created_at` (TIMESTAMPTZ).
- Primary key composta: `(run_date, rank)`.
- Indice secondario: `idx_top_value_picks_ticker_date` su `(ticker, run_date DESC)` per query "storia di un ticker nelle top picks".
- Retention: i record sono conservati per **365 giorni rolling**. Un job di pulizia (in scope di US-049 stessa, come `@Scheduled` separato a cadenza settimanale) elimina record con `run_date < now - 365 giorni`.
- Politica fuso orario: `run_date` è SEMPRE in UTC (no localizzazione).
- Validazione: prima del persist, il batch verifica che `rank` sia 1..30 univoco per ogni `run_date`.
- I `sources_json` espongono la provenienza del candidato per audit ("perché è in top 30?"): es. `{"screener": true, "13f_funds": ["BRK", "OAKMARK"], "news_scout": false, "panic_buy": true}`.
- La tabella è popolata esclusivamente dal `TopValuePicksJob` (US-048) — non esistono insert da API utente.
- Migration: gestita via tool migration relazionale già in uso (Flyway o equivalente, coerenza con TSK-001/002 baseline).

## UI Reference
N/A — storia di persistenza/dati; UI in US-051.

## Acceptance Criteria
- [ ] Migration crea la tabella `top_value_picks` con primary key composta + indice secondario.
- [ ] Insert di 30 record con stesso `run_date` e `rank` 1..30 univoco va a buon fine.
- [ ] Tentativo di insert duplicato su `(run_date, rank)` fallisce con violazione PK.
- [ ] Job di pulizia rolling elimina record con `run_date` più vecchi di 365 giorni.
- [ ] Query "ultimi 7 run_date" è performante (< 50 ms) grazie all'indice secondario.
- [ ] Il `verdict_payload` JSONB è leggibile con query SQL standard (test che proietta `verdict_class` dal JSONB).
