# TSK-134 — Test rate-limit batch — verifica fmp-batch non supera quota nel worst case + idempotenza job

## Cosa fare

1. Creare `TopValuePicksJobTest.kt` con Testcontainers PostgreSQL + WireMock + mock servizi upstream.
2. Test da implementare:
   - **Rate-limit worst case**: simulare un run con 50 ticker; verificare che le chiamate FMP non superino il `fmp-batch` limit (20/min) — misurare la durata e verificare che 50 chiamate in < 1 minuto vengano throttled.
   - **Idempotenza**: eseguire `TopValuePicksJob.run()` due volte per lo stesso `run_date` → il secondo run fa upsert, non insert duplicato; la tabella `top_value_picks` ha ancora 30 record (non 60).
   - **Errore singolo ticker**: 5 ticker mock lanciano eccezione → batch continua; `top_picks_run_log` registra `ticker_failed = 5`.
   - **Log WARNING durata > 3h**: simulare una durata > 3h (mock lento) → verifica log WARNING.
3. Verificare che `top_picks_run_log` abbia 1 record per ogni esecuzione del job.

## Acceptance Criteria

- [ ] Rate-limit: 50 richieste in < 1min → throttling verificato (durata > 2.5 min).
- [ ] Idempotenza: doppio run → stesso numero di record in `top_value_picks`.
- [ ] Errore singolo: `ticker_failed = 5` in `top_picks_run_log`.
- [ ] Log WARNING emesso per durata > 3h (mock).
- [ ] Run log: 1 record per esecuzione.
