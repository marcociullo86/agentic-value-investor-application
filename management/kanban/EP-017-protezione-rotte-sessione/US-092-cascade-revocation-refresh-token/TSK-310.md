# TSK-310 — QA Test cascade revocation refresh token

## Obiettivo

Coprire tutti gli Acceptance Criteria di US-092 con test di integrazione backend (JUnit 5 +
Testcontainers).

## Scenari obbligatori

1. **Riuso → 401 + cascade**: presentare un refresh token con `revokedAt != null` a
   `POST /api/auth/refresh` → risposta `401 invalid-refresh` + tutti i refresh token attivi dello
   stesso userId marcati `revoked_at = now()` nella tabella.

2. **Token legittimo altra sessione → 401 dopo cascade**: emettere due sessioni per lo stesso utente
   (login × 2), revocare tramite riuso sulla prima, poi presentare il token della seconda sessione →
   rifiutato con 401.

3. **Isolamento userId**: presentare un refresh token ruotato dell'utente A → i refresh token attivi
   dell'utente B non devono essere impattati.

4. **Idempotenza**: presentare lo stesso refresh token ruotato due volte → la seconda volta `revokedCount = 0`
   (bulk update su zero righe), nessun errore 500, nessuna revoca duplicata.

5. **Security event emesso**: verificare che `SecurityEventLogger.refreshTokenReuseDetected` venga
   chiamato con `userId`, `family = token.firstIssuedAt` e `revokedCount` corretto (spy o verifica su
   log strutturato nel test).

## Invarianti

- Il path "refresh token valido → nuovo access + nuovo refresh ruotato" passa senza regressioni
  (test esistenti US-075/US-076 non devono essere modificati nella logica, solo eventualmente nei nomi
  di campo se il DTO cambia forma — zero modifiche attese su questo path).
