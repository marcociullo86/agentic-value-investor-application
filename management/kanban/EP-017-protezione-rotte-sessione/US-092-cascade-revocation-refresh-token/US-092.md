# US-092 — Cascade revocation refresh token al riuso

## Descrizione
Come security auditor, voglio che il riuso di un refresh token già ruotato (potenziale token theft) provochi la revoca a cascata di TUTTI i refresh token attivi dell'utente, affinché un attaccante che ha esfiltrato un refresh token prima della rotation non possa continuare a mantenere una sessione parallela mentre la vittima opera normalmente. [^src: wiki/concepts/auth-guard-frontend.md §Storage dei token] [^src: wiki/concepts/fintech-security-compliance.md §5.5 — Threat model di baseline]

## Contesto
US-075 (`done`) AC §6 prescriveva esplicitamente: "Il riuso di un refresh token già ruotato causa revoca di tutti i refresh token dell'utente (simulato in test)". L'implementazione di `AuthService.refresh()` esegue la rotation singola (genera nuovo token, invalida il precedente) ma **non** propaga la revoca all'intero parco di refresh token attivi dell'utente. Il qa-dev ha aperto il gap formale `auth-cascade-revocation-missing` (2026-05-27) a valle di TSK-212. Questa US chiude il debito di compliance dell'AC §6 di US-075 senza riaprire quest'ultima (già `done` con AC §6 spuntato in modo presunto). [^src: wiki/gaps.md §2026-05-27 auth-cascade-revocation-missing]

## Business Rules
- **Detection riuso**: la presentazione al backend di un refresh token già marcato come ruotato/invalidato deve essere identificata in modo deterministico (tipicamente confronto su tabella refresh token con stato `ROTATED` / `REVOKED` / hash storico). [^src: wiki/concepts/auth-guard-frontend.md §Storage dei token]
- **Cascade revocation**: alla detection, tutti i refresh token attivi dell'utente — non solo quello presentato — devono essere invalidati lato server in modo atomico (bulk revoke per `userId`).
- **Risposta al client**: la richiesta di refresh che ha innescato la detection ritorna errore di autenticazione (es. 401 ProblemDetail RFC 9457) senza emettere nuovo access token né nuovo cookie. Il client tratta la risposta come "sessione scaduta" e applica il flusso di redirect a login coerente con US-076 (refresh fallito → `/login` con messaggio informativo). [^src: management/kanban/EP-017-protezione-rotte-sessione/US-076-rinnovo-automatico-token/US-076.md §Business Rules]
- **Audit trail**: l'evento di cascade revocation deve produrre un security event loggato (`refresh_token_reuse_detected` o equivalente, con `userId`, timestamp, e numero di token revocati), coerente con il logging eventi di sicurezza già attivo (EP-014 US-062). [^src: wiki/concepts/fintech-security-compliance.md §5.6 — Security events da loggare]
- **Idempotenza**: tentativi successivi sullo stesso refresh token (o su qualunque token dello stesso utente revocato dalla cascade) devono continuare a fallire senza side-effect aggiuntivi.
- **Non coinvolge altri utenti**: la revoca si limita ai refresh token dell'utente proprietario del token riusato; nessun impatto su altre sessioni di altri account. [^src: wiki/concepts/fintech-security-compliance.md §5.5 — Threat model di baseline]

## UI Reference
Nessuna — storia di sicurezza infrastrutturale. L'utente vittima percepisce la revoca come "sessione scaduta" sulle tab attive al primo refresh fallito (UX già coperta da US-073 / US-076).

## Acceptance Criteria
- [ ] Test backend: presentare un refresh token già ruotato a `POST /api/auth/refresh` produce errore di autenticazione (no nuovo access token, no nuovo cookie) E marca come revocati tutti i refresh token attivi dell'utente sulla tabella di persistenza.
- [ ] Test backend: dopo la cascade, qualunque altro refresh token dello stesso utente (es. la sessione "legittima" su altro device) presentato a `POST /api/auth/refresh` viene rifiutato con autenticazione fallita.
- [ ] Test backend: la cascade non revoca refresh token di altri utenti (isolamento per `userId`).
- [ ] Test backend: il riuso del medesimo refresh token ruotato per la seconda volta non genera errori 500 né revoche duplicate (idempotenza).
- [ ] Viene emesso un security event di tipo `refresh_token_reuse_detected` (o nome equivalente coerente con EP-014 US-062) con `userId`, timestamp e conteggio dei token revocati.
- [ ] Il gap `auth-cascade-revocation-missing` viene richiamato come origine in handoff/CQRL della US (chiusura formale resta a wiki-keeper).
- [ ] Nessuna regressione sui test esistenti del refresh-rotation singolo (US-075/US-076): il caso "refresh token valido non ruotato → nuovo access token + nuovo refresh ruotato" continua a passare.
