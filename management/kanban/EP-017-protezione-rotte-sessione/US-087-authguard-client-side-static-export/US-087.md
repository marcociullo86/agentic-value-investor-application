# US-087 — AuthGuard client-side compatibile static export

## Descrizione
Come utente autenticato, voglio che le rotte protette applichino in produzione la stessa semantica di guard (`returnUrl`, `/403`, sessione scaduta) anche con frontend static export, affinche' la UX di accesso resti coerente senza dipendere da middleware runtime non disponibile in produzione. [^src: design_&_architecture/decisions/ADR-026-frontend-authguard-static-export-runtime.md §Decisione]

## Business Rules
- In produzione resta il vincolo `output: 'export'`; il guard deve vivere in layer client-side (provider/hook/layout), non in middleware runtime.
- Semantica guard invariata rispetto a US-073: non autenticato -> `/login?returnUrl=...`, ruolo insufficiente -> `/403`, sessione scaduta -> logout silente + redirect login con stato esplicito.
- Backend resta security boundary autoritativo su auth/authz (defense-in-depth).
- `middleware.ts` puo' restare solo come supporto sviluppo locale (`next dev`), non come meccanismo di produzione.

## Acceptance Criteria
- [x] Con build statica servita dal backend, un utente non autenticato su rotta protetta viene rediretto a `/login?returnUrl=...`.
- [x] Dopo login riuscito, il redirect post-auth usa `returnUrl` e riporta alla rotta originaria.
- [x] Un utente autenticato senza ruolo richiesto viene rediretto a `/403`.
- [x] Sessione scaduta durante navigazione causa logout silente + redirect login con stato `sessionExpired`.
- [x] Le rotte protette sono gestite da guard client-side riusabile; il comportamento non dipende da `middleware.ts` in produzione.
- [x] E2E su bundle statico copre i percorsi `unauth`, `forbidden`, `sessionExpired`, `returnUrl`.
