# TSK-294 — BE: split deep analysis INGEST vs ANALYSIS

## Obiettivo
Separare la deep analysis in **due operazioni distinte** sul run-model async esistente (`deep_analysis_run`, TSK-293): **INGEST** (scarica i filing SEC + calcola/salva gli embedding, idempotente con skip dei filing già indicizzati, senza LLM) e **ANALYSIS** (invariata negli endpoint). L'analisi LLM (`invoke_llm=true`) su un ticker mai indicizzato **fallisce** con `reason = "not_indexed"` (errore guidato, niente auto-ingest); il verdetto deterministico (`invoke_llm=false`) non scarica né embedda nulla. Motivazione: gli embedding servono solo all'analisi LLM (Munger); indicizzare una volta e analizzare N volte riusando gli embedding persistiti in `filing_chunks`.

## Scope

### Migration V028 — colonna `kind`
- File `src/backend/src/main/resources/db/migration/V028__deep_analysis_run_kind.sql`.
- Aggiunge colonna `kind` (varchar — `INGEST|ANALYSIS`) a `deep_analysis_run`, con default `ANALYSIS` (back-fill delle righe esistenti) e `NOT NULL`.
- Aggiorna/aggiunge l'indice di lookup "latest" per filtrare per `kind` (es. `(ticker, kind, requested_at desc)`) e il partial index per i run `RUNNING` per il dedupe per-kind.

### Entity + Repository
- `DeepAnalysisRun` entity: aggiungere il campo `kind` (enum mappato a varchar).
- `DeepAnalysisRunRepository`:
  - `findFirstByTickerAndKindOrderByRequestedAtDesc(ticker, kind)` per il latest per-kind.
  - `findFirstByTickerAndKindAndStatus(ticker, kind, RUNNING)` per il dedupe per-kind.

### Split DeepAnalysisService — ingest / analyze
- Separare la pipeline in due percorsi:
  - `ingest(ticker)`: scarica i filing SEC + calcola/salva gli embedding tramite `FilingRagService`; **non invoca l'LLM**; ritorna un `IngestSummary` (`filingsTotal`, `chunksIndexed`, `chunksSkipped`, `indexedAt`).
  - `analyze(ticker, invokeLlm)`: invariata negli endpoint. Con `invokeLlm=true` su ticker mai indicizzato → lancia `FilingsNotIndexedException` (niente auto-ingest); con `invokeLlm=false` non scarica né embedda nulla.

### FilingRagService — skip idempotente
- L'indicizzazione salta i filing già presenti in `filing_chunks` (no ri-download / no ri-embedding dei filing invariati); conteggia `chunksIndexed` vs `chunksSkipped`.

### Executor dispatch per kind
- `DeepAnalysisRunExecutor` (`@Async("deepAnalysisExecutor")`): dispatch sul `kind` della riga:
  - `INGEST` → esegue `DeepAnalysisService.ingest(ticker)`, salva il summary nel record (riuso di `result_json` o colonna dedicata) e aggiorna `status`/`completed_at`.
  - `ANALYSIS` → esegue `DeepAnalysisService.analyze(ticker, invokeLlm)` come prima.
  - errore (incl. `FilingsNotIndexedException`) → `status = FAILED`, `error_reason`, `error_message`, `completed_at`.

### DeepAnalysisRunService — enqueueIngest + getLatestIngest
- `enqueueIngest(ticker)`:
  - dedupe su INGEST `RUNNING` per il ticker → riusa il run in corso.
  - altrimenti crea la riga `RUNNING` con `kind = INGEST`, `invoke_llm = false`, commit, invoca l'executor `@Async` via proxy Spring.
  - ritorna `{ runId, ticker, status, invokeLlm: false, kind: "INGEST" }`.
- `getLatestIngest(ticker)`:
  - nessun INGEST → `status = NONE`, `runId = null`, `summary = null`, `error = null`.
  - presente → mappa stato / `summary` / `error` nel DTO.
- `enqueue(ticker, invokeLlm)` (ANALYSIS) e `getLatest(ticker)` esistenti: filtrati per `kind = ANALYSIS`.

### Controller — 2 endpoint ingest
In `DeepAnalysisController` (accanto agli endpoint esistenti):
- `POST /api/analysis/{ticker}/deep/ingest` → `202`, body `DeepAnalysisRunStatusResponse` (con `kind = INGEST`).
- `GET /api/analysis/{ticker}/deep/ingest/latest` → `200`, body `IngestStatusResponse`.

### DTO
- `IngestSummary { filingsTotal, chunksIndexed, chunksSkipped, indexedAt }`.
- `IngestStatusResponse { ticker, status, runId?, requestedAt?, completedAt?, summary?: IngestSummary, error?: RunError }`.
- `DeepAnalysisRunStatusResponse`: aggiungere il campo `kind` (`INGEST|ANALYSIS`).
- Riuso di `RunError` esistente (`reason`/`message`).

### FilingsNotIndexedException → not_indexed
- Nuova eccezione di dominio `FilingsNotIndexedException` lanciata da `analyze` quando `invoke_llm=true` su ticker mai indicizzato.
- L'executor la mappa nel record `FAILED` con `error_reason = "not_indexed"`; il gestore RFC 9457 (US-021) la espone con `reason = "not_indexed"` dove pertinente.

### Test
- Unit/integration: `enqueueIngest` crea il run `RUNNING` (kind INGEST); dedupe INGEST non duplica; executor INGEST passa a `SUCCESS` col summary; skip idempotente (`chunksSkipped > 0` su re-ingest); `getLatestIngest` mappa `NONE`/`RUNNING`/`SUCCESS`/`FAILED`.
- `analyze(invokeLlm=true)` su ticker non indicizzato → `FAILED` con `reason = "not_indexed"`; `analyze(invokeLlm=false)` non scarica né embedda; `analyze(invokeLlm=true)` su ticker indicizzato riusa gli embedding.
- MockMvc: `POST .../deep/ingest` → 202 con body atteso (`kind: "INGEST"`); `GET .../deep/ingest/latest` → 200 nei vari stati.
- Verifica che gli endpoint ANALYSIS (`POST .../deep/runs`, `GET .../deep/latest`) e il sincrono `GET .../deep` restino invariati (no regressione contract test legacy).

## Acceptance Criteria
- [ ] Migration V028 applicata: colonna `kind` (`INGEST|ANALYSIS`, default `ANALYSIS`) su `deep_analysis_run`, indici lookup/dedupe filtrati per `kind`.
- [ ] `POST /api/analysis/AAPL/deep/ingest` → 202 con `{ runId, ticker, status: "RUNNING", invokeLlm: false, kind: "INGEST" }`, ritorno immediato.
- [ ] INGEST in background scarica filing + embedda senza LLM; idempotente: re-ingest salta i filing già in `filing_chunks` (`chunksSkipped > 0`).
- [ ] `GET /api/analysis/AAPL/deep/ingest/latest` mappa `NONE`/`RUNNING`/`SUCCESS`/`FAILED` con `summary`/`error` coerenti.
- [ ] Dedupe INGEST: secondo `POST .../deep/ingest` mentre il primo è `RUNNING` riusa lo stesso `runId`.
- [ ] `POST .../deep/runs?invoke_llm=true` su ticker mai indicizzato → `FAILED` con `error.reason = "not_indexed"` (no auto-ingest).
- [ ] `POST .../deep/runs?invoke_llm=false` su ticker mai indicizzato non fallisce con `not_indexed` e non scarica/embedda.
- [ ] Analisi LLM su ticker indicizzato riusa gli embedding persistiti (nessun ricalcolo).
- [ ] Endpoint ANALYSIS (`POST .../deep/runs`, `GET .../deep/latest`) e sincrono `GET .../deep` invariati (back-compat).

## Note implementative
- Dipende da TSK-293 (`deep_analysis_run` + `DeepAnalysisRunExecutor` + `DeepAnalysisRunService` + endpoint async già presenti).
- Stack: Kotlin 2.2 + Spring Boot 3.5. [^src: raw/tech_stack.md]
- Errori conformi RFC 9457 (US-021): `FilingsNotIndexedException` → `error_reason = "not_indexed"` nel record `FAILED`; il `GlobalExceptionHandler` la mappa inoltre a **409 Conflict** con extension `reason = "not_indexed"` per la chiamata sincrona, così il FE può proporre l'INGEST.
- Gli embedding sono persistiti in `filing_chunks`: l'INGEST è il solo produttore, l'ANALYSIS (LLM) il consumatore. Indicizzare una volta dopo ogni trimestrale/10-K, analizzare N volte.
