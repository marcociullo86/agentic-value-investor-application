# TSK-293 — BE: deep analysis run-model asincrono

## Obiettivo
Trasformare la deep analysis con LLM da sincrona ad asincrona: avvio via `POST` con risposta `202`, esecuzione in background con persistenza dello stato su `deep_analysis_run`, recupero dell'ultima esecuzione via `GET .../deep/latest` e dedupe dei run concorrenti sullo stesso ticker. L'endpoint sincrono `GET /api/analysis/{ticker}/deep` (TSK-118) resta invariato per back-compat.

## Scope

### Migration V027 — tabella `deep_analysis_run`
- File `src/backend/src/main/resources/db/migration/V027__deep_analysis_run.sql`.
- Colonne: `run_id` (PK, UUID), `ticker` (varchar, indicizzato), `status` (varchar — `RUNNING|SUCCESS|FAILED`), `invoke_llm` (boolean), `requested_at` (timestamptz), `completed_at` (timestamptz null), `result_json` (jsonb/text null — serializzazione di `DeepAnalysisResponse`), `error_reason` (varchar null), `error_message` (text null).
- Indice su `(ticker, requested_at desc)` per il lookup "latest" e indice/partial per i run `RUNNING` per il dedupe.

### Entity + Repository
- `DeepAnalysisRun` entity in `./src/backend/src/main/kotlin/com/valueinvesting/...` mappata su `deep_analysis_run`.
- `DeepAnalysisRunRepository` (Spring Data JPA):
  - `findFirstByTickerOrderByRequestedAtDesc(ticker)` per il latest.
  - `findFirstByTickerAndStatus(ticker, RUNNING)` per il dedupe.

### AsyncConfig
- `AsyncConfig` con `@EnableAsync` e un `ThreadPoolTaskExecutor` dedicato (bean qualificato, es. `deepAnalysisExecutor`) per non saturare il pool comune.

### DeepAnalysisRunExecutor (`@Async`)
- Metodo `@Async("deepAnalysisExecutor")` che esegue la pipeline esistente (`DeepAnalysisService.analyze(ticker, invokeLlm)` di TSK-118) e aggiorna la riga `deep_analysis_run`:
  - successo → `status = SUCCESS`, `result_json`, `completed_at`.
  - errore (incl. 404/422/503 RFC 9457) → `status = FAILED`, `error_reason`, `error_message`, `completed_at`.

### DeepAnalysisRunService (enqueue + dedupe + getLatest)
- `enqueue(ticker, invokeLlm)`:
  - se esiste un run `RUNNING` per il ticker → **dedupe**: ritorna quel run senza avviarne uno nuovo.
  - altrimenti crea la riga `RUNNING`, fa commit, e invoca l'executor `@Async` (l'invocazione async deve attraversare il proxy Spring — chiamare il bean executor, non un metodo `this`).
  - ritorna `{ runId, ticker, status, invokeLlm }`.
- `getLatest(ticker)`:
  - nessun run → `status = NONE`, `runId = null`, `result = null`, `error = null`.
  - run presente → mappa stato/`result`/`error` nel DTO.

### Controller — 2 endpoint
In `DeepAnalysisController` (accanto all'endpoint sincrono esistente):
- `POST /api/analysis/{ticker}/deep/runs?invoke_llm={bool}` → `202`, body `DeepAnalysisRunStatusResponse`.
- `GET /api/analysis/{ticker}/deep/latest` → `200`, body `LatestDeepAnalysisResponse`.

### DTO
- `DeepAnalysisRunStatusResponse { runId, ticker, status, invokeLlm }`.
- `LatestDeepAnalysisResponse { ticker, status, runId?, invokeLlm, requestedAt?, completedAt?, result?: DeepAnalysisResponse, error?: RunError }`.
- `RunError { reason, message }`.
- Riuso del DTO `DeepAnalysisResponse` esistente per il campo `result`.

### Innalzamento timeout sidecar
- Portare il timeout della chiamata al sidecar LLM da 120s a **180s** (config/property) per coprire la cold call dentro l'esecuzione asincrona.

### Test
- Unit/integration: `enqueue` crea il run `RUNNING`; dedupe non duplica run concorrenti; executor passa a `SUCCESS`/`FAILED`; `getLatest` mappa correttamente `NONE`/`RUNNING`/`SUCCESS`/`FAILED`.
- MockMvc: `POST .../deep/runs` → 202 con body atteso; `GET .../deep/latest` → 200 nei vari stati.
- Verifica che l'endpoint sincrono `GET .../deep` continui a funzionare (no regressione contract test legacy).

## Acceptance Criteria
- [ ] Migration V027 applicata, tabella `deep_analysis_run` creata con indici per latest e dedupe.
- [ ] `POST /api/analysis/AAPL/deep/runs?invoke_llm=true` → 202 con `{ runId, ticker, status: "RUNNING", invokeLlm: true }`, ritorno immediato.
- [ ] Run in background aggiorna la riga: `SUCCESS` con `result_json`/`completed_at`, oppure `FAILED` con `error_reason`/`error_message`.
- [ ] `GET /api/analysis/AAPL/deep/latest` mappa `NONE`/`RUNNING`/`SUCCESS`/`FAILED` con `result`/`error` coerenti.
- [ ] Dedupe: secondo `POST` mentre il primo run è `RUNNING` riusa lo stesso `runId`.
- [ ] Endpoint sincrono `GET .../deep` invariato (back-compat).
- [ ] Timeout sidecar LLM innalzato a 180s.
