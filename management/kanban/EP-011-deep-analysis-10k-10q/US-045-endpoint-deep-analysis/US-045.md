# US-045 — Endpoint `GET /api/analysis/{ticker}/deep`

## Descrizione
Come consumatore API, voglio un endpoint REST `GET /api/analysis/{ticker}/deep` che orchestri la pipeline completa di deep analysis (filing ingest → embedding → Munger inversione → news sentiment → price action → verdict cascade) e restituisca un payload strutturato unico, affinché il frontend e gli integratori esterni abbiano un'unica chiamata per ottenere il quadro qualitativo + quantitativo del ticker. [^src: wiki/concepts/analysis-api-pipeline.md §Pipeline]

## Business Rules
- Endpoint REST: `GET /api/analysis/{ticker}/deep?invoke_llm={true|false}` (param query opzionale, default `false`).
- **Policy LLM (2026-05-23, ADR-019 v2)**: l'endpoint risponde sempre con i campi deterministic (ruleId, Graham, DCF, MoS, price action, filings_used). I campi LLM-dependent (`deep_analysis_report` US-041, `sentiment_summary` US-042) sono popolati **solo se `invoke_llm=true`**. In modalità default (`invoke_llm=false`) restano `null` con un campo `llm_status: "NOT_INVOKED"`. Lo step LLM è quindi sempre user-initiated.
- Payload risposta JSON include: `ticker`, `generated_at`, `verdict_payload` (US-044, calcolato con `partial_basis=true` se LLM non invocato), `deep_analysis_report` (US-041, null se `invoke_llm=false`), `sentiment_summary` (US-042, null se `invoke_llm=false`), `price_action_snapshot` (US-043, sempre presente), `rule_engine_results` (13 ruleId di EP-010+EP-003, sempre presenti), riferimenti `filings_used` (lista filing ID + form type + filed_at), `llm_status` (`"INVOKED" | "NOT_INVOKED" | "CACHE_HIT" | "BUDGET_FROZEN"`), `llm_cost_estimate_usd` (stima a priori usata per la decisione del client).
- Orchestrazione: l'endpoint chiama in sequenza le US prerequisite (38, 39, 40, 43, 44 — deterministic) + (41, 42 — opt-in via `invoke_llm`). Senza LLM: tempo atteso < 2s. Con LLM (prima esecuzione su ticker nuovo): tempo atteso 30-90 secondi.
- Esecuzioni successive entro le finestre di cache (90gg filing, 24h news, 24h price action, 90gg report): tempo atteso < 2 secondi.
- Errori conformi RFC 9457 (US-021): ticker non risolvibile → 404; filing non disponibili → 422 con extension `reason = "no_sec_filings"`; LLM unreachable → 503 con extension `reason = "llm_unavailable"`.
- OpenAPI contract: l'endpoint è documentato nello YAML del contratto canonico con schema completo della risposta.
- Idempotenza: `GET` puro, nessun side-effect oltre alla popolazione di cache.
- Audit log: ogni esecuzione completa logga `(ticker, generated_at, cache_hits, llm_calls, total_duration_ms)` in `deep_analysis_event_log`.
- Wiki: la pagina `wiki/concepts/analysis-api-pipeline.md` esiste ma documenta solo `/api/analysis/{ticker}` standard; va estesa per coprire `/deep` (segnalato al wiki-keeper).

### Esecuzione asincrona (2026-05-29)
La deep analysis con LLM (cold call 30-90s, fino a 180s) passa da sincrona ad asincrona per evitare timeout HTTP lato client e consentire alla pagina di mostrare l'ultima esecuzione persistita all'apertura.

- **`GET /api/analysis/{ticker}/deep` (sincrono) resta invariato** come endpoint legacy / back-compat per integratori esterni e contract test esistenti. Nessuna rimozione, nessun breaking change.
- **Nuovo endpoint `POST /api/analysis/{ticker}/deep/runs?invoke_llm={true|false}`** (avvio asincrono):
  - Risponde **`202 Accepted`** immediatamente (fire-and-enqueue), senza attendere il completamento della pipeline.
  - Body: `{ runId, ticker, status, invokeLlm }` con `status ∈ {RUNNING, SUCCESS, FAILED}` (alla creazione tipicamente `RUNNING`).
  - L'esecuzione effettiva avviene in background (executor `@Async` dedicato) e popola/aggiorna la riga `deep_analysis_run`.
  - **Dedupe**: se per lo stesso `(ticker)` esiste già un run in stato `RUNNING`, il `POST` **non avvia una nuova esecuzione** ma riusa quella in corso e ne restituisce `runId` (idempotenza sul run attivo).
- **Nuovo endpoint `GET /api/analysis/{ticker}/deep/latest`** (recupero ultima esecuzione):
  - Risponde **`200 OK`** con l'ultima esecuzione persistita per il ticker dal DB.
  - Body: `{ ticker, status, runId|null, invokeLlm, requestedAt|null, completedAt|null, result, error }` con `status ∈ {RUNNING, SUCCESS, FAILED, NONE}`.
  - `status = NONE` (con `runId = null`) quando non esiste ancora nessun run per il ticker.
  - `result` è il payload `DeepAnalysisResponse` completo quando `status = SUCCESS`, altrimenti `null`.
  - `error` è `{ reason, message }` quando `status = FAILED`, altrimenti `null`.
- **Persistenza**: nuova tabella `deep_analysis_run` (migration V027) che traccia ogni esecuzione (`run_id`, `ticker`, `status`, `invoke_llm`, `requested_at`, `completed_at`, `result_json`, `error_reason`, `error_message`).
- **Comportamento pagina (no auto-rerun)**: all'apertura della pagina si mostra **l'ultima esecuzione dal DB** via `GET .../deep/latest` — nessuna ri-esecuzione automatica della pipeline. Una nuova esecuzione parte solo su azione esplicita dell'utente (`POST .../deep/runs`).
- Policy LLM, errori RFC 9457 e audit log (`deep_analysis_event_log`) restano applicabili: l'esito (incl. 404/422/503) del run asincrono è catturato nel campo `error` del record `deep_analysis_run` quando il run termina `FAILED`.

## Acceptance Criteria
- [ ] `GET /api/analysis/AAPL/deep` (senza `invoke_llm`) risponde 200 in < 2 s con payload deterministic completo + `llm_status: "NOT_INVOKED"` + campi LLM null.
- [ ] `GET /api/analysis/AAPL/deep?invoke_llm=true` su ticker già processato in cache risponde 200 in < 2 s con payload completo + `llm_status: "CACHE_HIT"`.
- [ ] `GET /api/analysis/AAPL/deep?invoke_llm=true` su ticker mai processato risponde 200 entro timeout configurabile (default 120 s) con tutti i campi popolati + `llm_status: "INVOKED"`.
- [ ] Con `llm.budget.frozen=true` e `invoke_llm=true` risponde 503 `LLM_FROZEN_BY_ADMIN` (RFC 9457) con `llm_status: "BUDGET_FROZEN"`.
- [ ] `GET /api/analysis/XYZNOPE/deep` su ticker invalido risponde 404 con body problem+json conforme RFC 9457.
- [ ] `GET /api/analysis/{ticker}/deep` su ticker senza filing SEC disponibili risponde 422 con `reason = "no_sec_filings"`.
- [ ] OpenAPI YAML del contratto canonico include lo schema completo.
- [ ] Contract-test e integration test coprono i quattro scenari principali (cache hit, cold call, ticker invalido, no filing).
- [ ] `deep_analysis_event_log` registra ogni esecuzione con cache_hits e llm_calls.

### AC esecuzione asincrona (2026-05-29)
- [ ] `GET /api/analysis/{ticker}/deep` (sincrono) continua a rispondere come prima (back-compat preservata, contract test legacy verde).
- [ ] `POST /api/analysis/AAPL/deep/runs?invoke_llm=true` risponde **202** con body `{ runId, ticker, status: "RUNNING", invokeLlm: true }` e ritorna immediatamente (no attesa della pipeline).
- [ ] Il run in background popola `deep_analysis_run`: a completamento `status` passa a `SUCCESS` con `result_json` valorizzato e `completed_at` settato; su errore passa a `FAILED` con `error_reason`/`error_message`.
- [ ] `GET /api/analysis/AAPL/deep/latest` su ticker mai analizzato risponde **200** con `status: "NONE"`, `runId: null`, `result: null`, `error: null`.
- [ ] `GET /api/analysis/AAPL/deep/latest` mentre un run è `RUNNING` risponde **200** con `status: "RUNNING"` e `result: null`.
- [ ] `GET /api/analysis/AAPL/deep/latest` dopo un run riuscito risponde **200** con `status: "SUCCESS"` e `result` = payload `DeepAnalysisResponse` completo.
- [ ] `GET /api/analysis/AAPL/deep/latest` dopo un run fallito risponde **200** con `status: "FAILED"` e `error: { reason, message }`.
- [ ] **Dedupe**: due `POST .../deep/runs` ravvicinati mentre il primo run è ancora `RUNNING` → il secondo riusa il run in corso (stesso `runId`), nessuna seconda esecuzione concorrente sullo stesso ticker.
- [ ] All'apertura pagina viene servita l'ultima esecuzione dal DB senza ri-eseguire automaticamente la pipeline (no auto-rerun).
- [ ] OpenAPI YAML del contratto canonico include i due nuovi path (`POST .../deep/runs`, `GET .../deep/latest`) e i nuovi schema (`DeepAnalysisRunStatusResponse`, `LatestDeepAnalysisResponse`, `RunError`) riusando `DeepAnalysisResponse`.
- [ ] Timeout sidecar/LLM innalzato a 180s per coprire la cold call dentro l'esecuzione asincrona.
