# TSK-297 — INFRA: sidecar embeddings su GPU NVIDIA (Podman CDI)

## Obiettivo
Dare al sidecar embeddings (TSK-099) la possibilità di girare su **GPU NVIDIA** via Podman + CDI, mantenendo il path CPU come default (CI / dev senza GPU non devono fallire). Su VRAM piccola (es. NVIDIA T600 4GB) servono fp16, batch ridotti e tuning dell'allocatore CUDA per evitare OOM. La selezione CPU/GPU è offerta dallo script di avvio.

## Scope (cosa è stato fatto)

### `app.py` — device + fp16 + /health
- `_resolve_device()`: usa **CUDA** se `torch.cuda.is_available()` (GPU iniettata via CDI), altrimenti **CPU**; override manuale con env `EMBEDDING_DEVICE`.
- Caricamento modello con `device=...`; su GPU applica **fp16** (`model.half()`) di default — dimezza VRAM e calcolo, indispensabile su schede piccole dove fp32 + batch grandi causano CUDA OOM nel buffer di attention (O(batch·seq²)). Disattivabile con `EMBEDDING_FP16=false`.
- `GET /health` espone ora il **`device`** effettivo (`{"status":"ok","model":...,"device":"cuda|cpu"}`) per diagnosi.

### `docker-compose.gpu.yml` — override GPU (layer sopra il compose base)
- Servizio `embeddings-sidecar`: `devices: ["nvidia.com/gpu=all"]` (device CDI → flag `--device nvidia.com/gpu=all`), env `EMBEDDING_DEVICE=cuda`, `EMBEDDING_FP16=true`, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` (riduce frammentazione allocatore CUDA → meno OOM su VRAM piccola).
- Tuning lato `app` in modalità GPU via env relaxed-binding Spring: `EMBEDDINGS_BATCH_SIZE=4` (il T600 ha 4GB; con fp16 + batch 4 + chunk ~1500 token si resta nei 4GB) e `EMBEDDINGS_SIDECAR_TIMEOUT_SECONDS=300` (GPU veloce → timeout più corto). In modalità CPU (override non applicato) restano i valori di `application.yml`.
- Documentati i prerequisiti host one-time nella podman machine: `nvidia-container-toolkit` + spec CDI (`sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`, verifica `nvidia-ctk cdi list`).

### `requirements.txt` / `Dockerfile` — torch cu126
- `torch` **non** è in `requirements.txt`: viene installato esplicitamente dal canale **CUDA cu126** nel Dockerfile (il wheel torch di default su PyPI è compilato per una CUDA troppo recente per il driver → "NVIDIA driver too old"). `sentence-transformers` lo trova già soddisfatto.

### Script di avvio — prompt CPU/GPU
- `start-agentic-value-investor.ps1` / `.sh`: alla scelta del backend del sidecar chiedono **CPU o GPU**; su GPU aggiungono `-f src/docker/docker-compose.gpu.yml` allo stack compose. Default **CPU** su Invio (non fallisce dove la GPU non è configurata).

## Acceptance Criteria
- [x] Su host con GPU configurata, `podman-compose -f docker-compose.yml -f docker-compose.gpu.yml up -d` avvia il sidecar su CUDA.
- [x] `GET /health` riporta `"device":"cuda"` quando la GPU è iniettata, `"cpu"` altrimenti.
- [x] fp16 attivo di default su GPU; il sidecar resta nei 4GB di VRAM del T600 (batch 4 + `expandable_segments`).
- [x] Il compose base resta CPU-safe (CI / dev senza GPU non falliscono).
- [x] `torch` installato dal canale cu126 (nessun errore "NVIDIA driver too old").
- [x] Lo script di avvio offre la scelta CPU/GPU con default CPU.
