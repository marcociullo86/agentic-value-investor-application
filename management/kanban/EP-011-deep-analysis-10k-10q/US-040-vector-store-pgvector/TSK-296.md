# TSK-296 — BE: fix trasporto `EmbeddingService` (body JSON vuoto → 422)

## Obiettivo
Le chiamate `POST /embed` dal backend al sidecar Python (TSK-100) fallivano con **422 Unprocessable Entity** (`{"loc":["body"],"msg":"Field required","input":null}`): il body JSON arrivava **vuoto** al sidecar FastAPI. Causa: la request factory di default (`JdkClientHttpRequestFactory`) usa un body-publisher in streaming e, quando la `Content-Length` non è nota a priori, può inviare `noBody()`. Il fix forza una factory che bufferizza il body.

## Scope (cosa è stato fatto)

### `EmbeddingService` — request factory esplicita
- Il `RestClient` del sidecar è costruito con `.requestFactory(buildRequestFactory(timeoutSeconds))`.
- `buildRequestFactory` usa **`SimpleClientHttpRequestFactory`** (`HttpURLConnection`): bufferizza interamente il body e imposta `Content-Length` prima di inviare → il sidecar riceve il JSON completo, niente più 422.
- **Timeout preservati** (connect + read) dal valore `embeddings.sidecar.timeout-seconds` (hardening TSK-100, wave-04 review): un sidecar bloccato non deve pinnare indefinitamente i thread di indicizzazione RAG.

## Acceptance Criteria
- [x] `EmbeddingService.embed(listOf("hello"))` invia il body JSON completo al sidecar (no più 422 "Field required").
- [x] Il sidecar `POST /embed` riceve `{ "texts": [...] }` con `Content-Length` valorizzato.
- [x] Connect/read timeout invariati rispetto a TSK-100 (driven da `embeddings.sidecar.timeout-seconds`).
- [x] Nessuna regressione su batching / aggregazione vettori 1024-dim.
