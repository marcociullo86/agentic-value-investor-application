# US-040 — Vector store pgvector con embedding Arctic locali

## Descrizione
Come sistema backend, voglio chunking, embedding e persistenza dei filing 10-K/10-Q dentro PostgreSQL tramite l'estensione pgvector, usando un modello di embedding locale Snowflake/snowflake-arctic-embed-l-v2.0 caricato via HuggingFace, affinché le query semantiche delle US successive (Munger inversione, news classifier) operino su un retrieval RAG efficiente senza dipendere da servizi vettoriali esterni. [^src: wiki/concepts/analysis-api-pipeline.md §Pipeline]

## Business Rules
- Estensione database: `CREATE EXTENSION IF NOT EXISTS vector` su PostgreSQL 17 (già in tech stack).
- Nuova tabella `filing_chunks` con almeno colonne (`id`, `filing_blob_id` FK, `chunk_index`, `chunk_text`, `embedding` (vettore 1024-dim), `created_at`).
- Chunking: dimensione chunk 6000 caratteri, overlap 400 caratteri (parametri esposti in `application.yaml` per tuning futuro).
- Modello embedding: `Snowflake/snowflake-arctic-embed-l-v2.0` (1024 dim, 8192 token context, MTEB ~67), caricato via HuggingFace.
- L'embedding gira **localmente** (sulla macchina backend o container dedicato); nessuna chiamata di rete a servizi terzi per il calcolo embedding.
- Configurazione: il nome modello è esposto in `application.yaml` (`embeddings.model.name`) per consentire A/B test futuro con alternative (es. Qwen3-Embedding-4B) senza ricompilare.
- Indice vettoriale: HNSW su colonna `embedding` con parametri `m=16`, `ef_construction=64` (default pgvector raccomandato per uso generale; tunable in migration).
- Idempotenza: ricostruire i chunk di un filing già processato non duplica righe (chiave composta `filing_blob_id` + `chunk_index`).
- Politica costi: l'embedding di tutti i chunk di un singolo 10-K (tipicamente 30-80 chunk) deve completare in < 30 secondi su hardware standard (M-series Mac o equivalent x86 con 16GB RAM).
- Wiki spec di riferimento: pagine concept dedicate "pgvector store" e "Arctic embed integration" non esistono ancora; nel frattempo `wiki/concepts/analysis-api-pipeline.md` documenta il flusso end-to-end. Segnalata necessità di promozione al wiki-keeper.

### Nota — sidecar embeddings: fix trasporto + supporto GPU (2026-05-30)
Hardening del sidecar embeddings (TSK-099/100) emerso durante la messa in esercizio della pipeline RAG:
- **Fix trasporto (be)**: le chiamate `POST /embed` dal backend fallivano con **422** perché il body JSON arrivava vuoto. Causa: la `JdkClientHttpRequestFactory` di default inviava `noBody()` quando la `Content-Length` non era nota a priori. Fix: `EmbeddingService` usa esplicitamente `SimpleClientHttpRequestFactory` (bufferizza il body + `Content-Length`), preservando i connect/read timeout di TSK-100. → TSK-296 (layer be, `depends_on: TSK-100`).
- **Supporto GPU NVIDIA (infra)**: il sidecar può ora girare su GPU via Podman + CDI (`nvidia-container-toolkit` + spec CDI), con override `docker-compose.gpu.yml` separato (compose base resta CPU-safe). `app.py` auto-rileva il device e applica fp16 su CUDA; `/health` espone il `device`. Tuning per VRAM piccola (T600 4GB): batch-size 4, timeout 300s, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, `torch` pinnato al canale cu126. Gli script di avvio (`start-agentic-value-investor.ps1`/`.sh`) chiedono CPU/GPU (default CPU). → TSK-297 (layer infra, `depends_on: TSK-099`).
